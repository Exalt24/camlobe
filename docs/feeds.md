# Feeds: sources, mapping and what a run records

`python manage.py ingest_feed <supplier> <one source>`. Secrets come from environment variables, never from the command line.

| Source | Flags | What it does |
|---|---|---|
| Local CSV or XML | `--file PATH` | reads it line by line (CSV) or as a stream (XML) |
| SFTP | `--sftp-host H --sftp-path /feed.csv --sftp-user U --sftp-password-env NAME --sftp-host-key SHA256:...` | checks the host key against the fingerprint you give, downloads to a temporary file, checks the size before and after, then reads it like a local file |
| Paged REST | `--rest-url URL [--token-env NAME] [--page-size N] [--rate-limit PER_SECOND]` | `GET url?offset=&limit=` answering `{"items": [...], "total": N}` |
| SOAP | `--soap-wsdl URL [--page-size N]` | calls `GetCatalogPage(offset, limit)` through zeep |
| A site with a login | `--scrape-config FILE.json` | logs in and reads the product table page by page: see [Scraping a site](#scraping-a-site) |

Every source also takes `--snapshot` (this supplier's feed lists everything it offers, see [Full snapshots](#full-snapshots-and-delisting)) or `--incremental` (it does not), and `--allow-mass-delist`.

## Mapping

Columns are matched by name, never by position, after lower casing and dropping punctuation. `item_number`, `PartNo`, `sku` and `Item Number` all mean the part number. A reordered file loads the same rows, and a rename to a known alias loads as before. A required column (part number, brand, cost) that no header maps to fails the run before a row is written, with the headers the feed does have in the message. Two headers for one REQUIRED field (`SKU` and `MPN`) is also refused, because which one is the supplier's number is a decision and not a default. Two headers for an OPTIONAL field are ordinary (`UPC` and `EAN` side by side): a row takes the first valid GTIN from left to right, or the first non empty value when none is valid (so a bad GTIN is still flagged and not dropped), and the first non empty description. The run's notes say which columns were doubled and how often each was used (`doubled_columns`, `column_choices`). Columns that map to nothing are listed in the run's notes.

Costs are parsed with `Decimal` into integer cents. `12,50` (a decimal comma looks like a thousands separator), `12.505` (half a cent), `-3`, `N/A` and anything above ten million dollars are rejected rows, never guessed. So is a cell holding TWO amounts (`$20 $15`, a struck price and a new one): gluing them gave 2015 dollars, now it is a `bad_cost` row with its raw text kept. **Known limit:** spaces that group thousands (`1 234.50`) are accepted, so two bare whole amounts with no currency sign and no cents (`12 345`) read as one; refusing the grouping would refuse an ordinary price.

## Encodings

CSV lines are decoded one at a time: UTF-8 first, windows-1252 when that fails, so one pasted latin line does not turn every accent in the file into noise. A byte windows-1252 does not define rejects that row (`undecodable_bytes`). A UTF-8 byte order mark is skipped, and the delimiter (comma, semicolon, tab or pipe) is read from the header line. A UTF-16 or UTF-32 file (Excel's "Unicode Text" export is UTF-16) is found by its byte order mark, or without one by a NUL in every second byte, and decoded whole; the run's notes say `encoding`. One stray NUL in an ordinary file is not mistaken for that, and a NUL inside any row of any source rejects that row (`nul_character`), because Postgres cannot store it. A row with the wrong number of cells is rejected (`column_count`).

XML is parsed with DTDs and entities forbidden. A record is a direct child of the root. Its fields are its own attributes, then its child elements by name, and an attribute of a child as `child@attribute`. A namespace is dropped from every name: `<catalog xmlns="urn:x"><item><sku>` and `<c:sku>` are both `sku`.

## What a run records

Every run is a row in `catalog_pipelinerun`: kind, supplier, source, status (`running`, `succeeded`, `partial`, `failed`), counts (read, written, unchanged, rejected), up to 50 errors and notes (encoding, resume point, retries, unmapped columns). Rejected rows are kept with their position, reason and raw text. `GET /api/feed-runs/` shows them.

## Secrets

A password, a bearer token, a proxy's credentials and the query values of a source URL never reach the database, the open `/api/feed-runs/` or the log. An exception's text is not under our control (`requests` puts a whole proxy URL, password included, into an `InvalidURL` message), so each adapter NAMES the secrets it was configured with (`secret_values()`) and the runner passes every error, gap message, note and log record through one redactor (`catalog/ingest/redact.py`) before it is stored: the secret is replaced by `[redacted]`, also in its percent encoded, form encoded and escaped forms, and so is every piece of it of four characters or more that a URL parser cuts it into at a backslash, slash, question mark, hash, at sign, colon or percent form (`requests` quoted the first half of a proxy password with a backslash: `'[redacted]:Zq9pass' is not a valid host or port`). A proxy URL is read up to its LAST at sign, so a hash or slash in the password cannot hide it. A piece shorter than four characters is not taken out of other text; a URL is removed whole, its host and scheme are no secret. The tests plant a distinctive secret in every configurable place of the scraper, REST, SFTP and SOAP adapters, make each raise an exception that repeats it, and search everything the database holds.

The identity of a source (`source_ref`, and with it the checkpoint) hides the value of a query parameter whose NAME says it is a secret (`api_key`, `token`, `sig`, `session`, `password` and the like). A filter such as `?cat=brakes` stays, so two sources that differ only in a filter keep two checkpoints. **Known limit:** a secret in a parameter whose name says nothing (`?k=...`) stays in the `source_ref`, because it cannot be told from a filter value and hiding both would merge two sources into one checkpoint; it is still taken out of every message. Put a secret in a named environment variable, not in a URL.

## Restart and re-run

- Each batch of 1000 rows is one transaction holding its rows, its rejected rows, the run counters and the checkpoint.
- A source is skipped when its content hash equals the last complete run's, and a skipped run delists nothing. A file with the same name and new content is read from the start, and only the rows that changed are stored.
- A row is stored when its content differs from the newest stored version of the same supplier part number. A price that goes from A to B and back to A stores three versions, so the current price is the last one.
- Each source row also has an idempotency key (supplier, source, position, content hash, and the PASS: the id of the run that began it) with a unique constraint, which is what stops rows after a gap landing twice when they are read again in the same pass. A new file version and every restarted walk of a live site begin a new pass, so run 3 does not find run 1's key for a price that returned to 10.00 and counts it unchanged while 12.00 is the newest version.
- A run left `running` by a dead process is closed as failed at the next start. Two runs of one source cannot overlap (Postgres advisory lock).

## Paged sources

Requests are spaced by the rate limit. A timeout, connection error, a body cut after its headers (`ChunkedEncodingError`), 429 or 5xx is retried with exponential backoff, a `Retry-After` is honoured up to the cap, as a number of seconds or as an HTTP date (REST, SOAP and the scraper read it in one function; SOAP through its transport, since zeep's error carries no headers). Every other error `requests` raises is either retried the same way and then a gap (anything transient, also one a later `requests` adds) or, for a configuration error (an invalid URL, header or proxy, a missing schema or dependency), a failed run with the fixed phrase `E_REQUEST_INVALID` and none of the exception's text. A page that still fails, or a 4xx retrying cannot fix, becomes a gap: the run is `partial`, the checkpoint stops at the gap, the pages after it are still read, and the next run adds only the missing page. A 401 or 403 stops the run at once. Three failed pages in a row mean the endpoint is down. A page shorter than asked for in the middle of a known total stops the run, because the server capped the page size and carrying on would skip rows.


When the total is unknown (the server sends none), a short page proves nothing, because the server may cap its pages. Paging goes on, each request starting where the last answer ended, until a page comes back empty. With a known total the guard above stays. A page whose items are exactly those of a page already read in the same run (a server that answers every offset with page 0) is a gap coded `E_PAGE_REPEATED`: its rows are not stored a second time, the run is `partial`, the checkpoint stops there, and the rows that belong at that offset are reported as missing (positions in the error). With no total, or three in a row, the run stops. A page of one item is never called a repeat, since a feed may list the same row twice. This detects a page repeated whole, not pages that overlap.

**Resume is by offset, so the source must keep its order.** A resumed paged run starts at the page of the checkpoint and skips the rows already stored by position. That is only right if the API returns its items in a stable order (by id, by creation): if the supplier orders by something that changes between two runs (price, popularity, last edit), a part that moves from after the resume point to before it is never read, and on a `--snapshot` supplier it is then delisted. This is a stated precondition of the REST and SOAP adapters, **not fixed here**, because it needs a partial run and a reorder between two runs, and the cure (reading every page again after a partial run) would give up "the next run adds only the missing page". The scraper has no such precondition: it never resumes by position, see below.

A REST answer is parsed from its bytes as JSON (UTF-8, RFC 8259), whatever its Content-Type says: `requests` would read a `text/plain` or `text/json` answer with no charset as ISO-8859-1 and store every accent as mojibake.

## Full snapshots and delisting

A supplier whose feed lists everything it offers is flagged once with `ingest_feed <supplier> --snapshot ...` (and unflagged with `--incremental`). While flagged, each batch also records which supplier parts the pass read, including rows that did not change (they store no raw row, so nothing else says they are still listed). When a pass over the source finishes and the run is `succeeded`, every listing of that supplier that the pass did not read gets `delisted_at`, and a delisted listing that the pass reads again is relisted. The supplier's snapshot is its latest completed pass over any of its sources, and a pass that has not finished never replaces it: what a pass reads is kept apart (`staging`) and swaps in, with the completion time, only when the run completes, so one partial run of a restarted source leaves the last completed pass as it was and delists nothing, so a feed that arrives under a new file name every day works, and a supplier that sends two feeds at the same time (brakes in one file, filters in the other) must not be flagged.

Delisted listings are ignored by the search document (`suppliers`, `supplier_count`, `lowest_cost_cents`), by the REST part detail (`sources` holds the live ones, `delisted_sources` the others) and by `purchase_order_for`, which refuses a part that only a delisted listing offers with `E_DELISTED`. The part itself stays in the catalog and in search. A delisting bumps the part's search version, so the next index sync sends it.

What keeps a bad file from emptying a catalog: a partial or failed run delists nothing; a pass that rejected a row it could not read (`column_count`, `undecodable_bytes`, `nul_character`) delists nothing, since that row might have been any part; a pass that read no part delists nothing; and a pass that would delist more than half of a supplier's listings (when it has at least ten) delists nothing unless `--allow-mass-delist` is given, since a truncated file reads cleanly. The run's notes say what happened (`snapshot`: `delisted`, `relisted`, `delist_refused`). The match step and `resolve_review` check new listings against the latest snapshot too, so a part ingested before the newer feed but matched after it is delisted at once. A row rejected only for its cost still counts as listed.

## Scraping a site

`catalog/ingest/scrape.py`, `ScrapeAdapter`, behind the same interface as the others. **It was built and tested against a local fake site only and has never been run against a real one.** Use it only on a site whose owner has allowed it, under terms you have read: `robots.txt` is checked and a challenge ends the run, and neither is permission.

`ingest_feed <supplier> --scrape-config shop.json`, where the file is:

```json
{
  "start_url": "https://shop.example/catalog?page=1",
  "login_url": "https://shop.example/login",
  "username_env": "SHOP_USER",
  "password_env": "SHOP_PASS",
  "session_cookie": "sid",
  "cookie_jar": "shop.cookies",
  "table_selector": "table.products",
  "next_selector": "a[rel~=next i]",
  "delay_seconds": 1.0,
  "user_agent": "camlobe-feed/1.0 (contact: you@example.com)",
  "proxy_envs": ["SHOP_PROXY"]
}
```

`username_env`, `password_env` and `proxy_envs` are the NAMES of environment variables. The credentials are read in the constructor and kept in private attributes; the runner takes them out of every message it stores or logs (see [Secrets](#secrets); a test plants one in every place and searches the database). A proxy URL with a password goes in `proxy_envs`; `proxies` refuses one. A proxy URL that is not a URL (no scheme, a scheme other than http, https, socks5 or socks5h, a bad host, a port outside 1 to 65535) is refused with `E_PROXY_URL` and a fixed phrase that quotes nothing of it: a literal one when the config loads, one read from the environment as a failed run before any request. The other settings and their defaults are the fields of `ScrapeConfig`.

| Step | Rule |
|---|---|
| robots.txt | fetched once and every URL checked (`respect_robots`, on by default); up to five redirects are followed, to another host too, and the rules of the file they end on apply to the site (RFC 9309); the site's `Crawl-delay` raises the pause; a missing file, a sixth redirect or a redirect with no place to go means no rules, a server error anywhere on the way reads as everything disallowed (`E_ROBOTS_UNAVAILABLE`); a refusal is `E_ROBOTS` |
| Login | the form with the password field is read (its relative `action` is resolved like a next link: against the page's `<base href>` or the address the login page was served from), every hidden field (the CSRF token among them) is posted with the credentials; no `csrf_field` in the form is `E_LOGIN_FORM`, a refused login `E_LOGIN_FAILED` |
| Session | the cookie jar can be saved to `cookie_jar` and loaded next run (it holds a live session: it is gitignored, written with owner only rights where the system allows, and is a secret); an expired session (a redirect to the form, a 200 page with a password field and NO product table, or a 401) is logged in again ONCE; a page that has the product table is a data page whatever else is on it, so a sign in box in the header of an open catalog is not a login wall, the second expiry ends the run `E_SESSION_EXPIRED` |
| Pace | `delay_seconds` between any two requests; a 429 waits what `Retry-After` says, in seconds or as an HTTP date (a wait above `backoff_cap` is not waited: `E_RATE_LIMITED`), a 5xx or a timeout is retried with exponential backoff, then `E_SERVER_ERROR` or `E_UNREACHABLE`; a body cut after its headers is retried the same way, then `E_PAGE_TRUNCATED`, and any other error from `requests` is a coded gap (`E_TRANSPORT`) or, for a configuration error, a failed run (`E_REQUEST_INVALID`) |
| Proxies | requests go through the first live proxy; one that refuses or drops the connection is skipped for the next; all failing is `E_PROXY_UNAVAILABLE` and nothing goes direct. The system proxy settings and `.netrc` are ignored. `socks5` and `socks5h` need PySocks, which `requirements.txt` installs (`requests[socks]`); if it is ever missing the run fails with the fixed phrase `E_REQUEST_INVALID`, never a stored traceback |
| Pages | the `next` link (the default selector matches the rel TOKEN `next`, ignoring case: `nofollow next` and `NEXT` are next links, `nextpage` is not; a selector in the config is used as written), same site only (`E_OFFSITE`), never twice (`E_PAGE_LOOP`), up to `max_pages` (`E_TOO_MANY_PAGES`); redirects are followed by hand, three hops, same site. A relative link is resolved against the page's first `<base href>`, else against the address the page was SERVED from (after a trailing slash redirect that is not the address asked for), and a page is remembered under both names for the loop and self link checks. A next link that is not a page is the end of the walk: an empty href, `#`, `javascript:`, a link whose class says `disabled` or whose `aria-disabled` is true, or a link back to the page itself. A fragment is dropped before pages are compared, and a link to a DIFFERENT page already read stays a loop |
| Whole pages | the walk ends as a success only when the site said it ended. The page's own tags are read as the site sent them (the lxml tree would close a cut table): a table the site never closed, a page that does not reach its closing body or html tag, or a body shorter than the `Content-Length` it announced is `E_PAGE_TRUNCATED`, and nothing is read from a table that was cut. A table with no rows on the first page is a failed run, `E_PAGE_EMPTY`, and on a later page a gap; `allow_empty: true` says a supplier may list nothing and accepts both. A gap makes the run `partial`, which delists nothing and never completes the checkpoint. A page of a site that never writes its closing `</body>` or `</html>` is therefore always `partial`: not fixed, a site like that cannot show it finished |
| Encoding | the page bytes are decoded as the page says: byte order mark, then the charset of the Content-Type, then a meta tag, then UTF-8, never ISO-8859-1 by default (`requests` does that for any `text/*` with no charset). A latin-1 label is read as windows-1252, as a browser does. Bytes that fit nothing the page declares are `E_PAGE_ENCODING`, and nothing is stored: a legacy page that declares no charset and is not UTF-8 is refused, not guessed |
| Table | the table's OWN rows and cells are read (a table nested in a cell is that cell's text; a `th` in a body row is a cell like a `td`; a `colspan` fills that many columns, the extra header columns are named `Price (2)`; the header is the first `thead` row with any text, so a second one such as a filter row is skipped; a body row of `th` cells only is a heading). **Known limit, not fixed:** `rowspan`, and a stray closing table tag with a cut inside a price cell. Cells under the header text become the record, which the usual header mapping reads (`Part No`, `Brand`, `Description`, `Price`); a row with the wrong number of cells is rejected `column_count`; the HTML is read with BeautifulSoup on the lxml parser, which closes a cell the way a browser does |

A block or challenge is never data. HTTP 403 is `E_BLOCKED` and is not retried; a 200 page that carries a challenge marker (`challenge_markers`: "checking your browser", `g-recaptcha`, "captcha", "access denied" and a few more) anywhere outside the product table is `E_CHALLENGE`; a page with no product table is `E_UNEXPECTED_PAGE`. Each ends the run as a gap, so the run is `partial`, the rows read before it are kept, nothing is stored from the page that stopped it, and nothing is done to get past it. A product whose description says "captcha" is a product: the table is left out of the marker scan.

**A resume never skips rows by position.** The order of a live site changes between two runs (a part is withdrawn, a price re-sorts the list), so row N of the earlier run is not row N now, and skipping N rows would skip rows the site still offers. The adapter says it is not resumable (`resumable = False`), the runner starts such a source over (checkpoint position, completed flag and the staged set of parts the pass has seen; the last completed pass stays what the delisting reads), and every run walks from the FIRST page, as a new pass; what is already stored is not stored again, because a row equal to the newest stored version of its part is unchanged. The cost is the pages read again after a partial run. The fingerprint is empty (a live source), so a finished run is read again by the next one too.
